## Introduction

We talked about [duplicate node names](./2025_03_14.md) earlier, so are there duplicate topic names too?

Yes, dude, yes there are☝🤓

---

Just like duplicate node names, in ROS2 topic names can clash too. Between different nodes, communication all depends on topics, and when topic names clash the system doesn't throw an exception, but nodes tied together by the **same topic name** may **not belong** to the same communication logic, which scrambles the communication and can even throw errors. In that case you may need to give the same topic name different values.

Unlike node names, though, some scenarios need you to avoid duplicate topic names, while other scenarios need you to change different topic names to the same one so that some feature works. So duplicate topic names are **allowed** in certain cases.

For example, two nodes belong to the same communication logic, but because the topic names differ between them, communication fails. In that case you need to change the two nodes' topic names from different to the same.

So how do we change a topic name in ROS2?

## The strategies

As with duplicate node names, the same two common strategies apply:

1. **Namespace**, i.e. putting a prefix on the topic's name; the prefix can be several levels deep, usually in the format of /xxx/yyy/zzz
2. **Name remapping**, giving the topic an alias;

::: caution Note
When you set a topic name through a namespace, you need to make sure the topic type is **not a global topic**, otherwise it can't be changed.
For details on topic types see [the description below](./2025_03_15.md#topic-types-and-how-they-relate-to-topic-names)
:::

## How to do it

As with duplicate node names, there are generally the following common approaches:

### 1. Setting the node name with ros2 run

#### ①. Set the namespace

The syntax is:

```bash
ros2 run <package name> <node name> --ros-args --remap __ns:=<namespace>
```

For example:

```bash
ros2 run turtlesim turtlesim_node --ros-args --remap __ns:=/t1
```

Before running that command in a terminal, checking the topic information with `ros2 topic list` shows information containing the following result:

```txt
/turtle1/cmd_vel
```

And after running that command in a terminal, checking the topic information with `ros2 topic list` shows information containing the following result:

```txt
/t1/turtle1/cmd_vel
```

::: info Isn't this step the same as when we changed duplicate node names?
Indeed🤣 because a node changed this way has the namespace prefix added to its topics already — that is, every **non-global topic** under the node gets the namespace prefix — so for duplicate topic names, the fix **here** is no different from duplicate node names. As for what a **global topic** is, see [the description below](./2025_03_15.md#topic-types-and-how-they-relate-to-topic-names)
:::

#### ②. Set name remapping

The syntax is:

```bash
ros2 run <package name> <node name> --ros-args --remap <original topic name>:=<remapped topic name>
```

For example:

```bash
ros2 run turtlesim turtlesim_node --ros-args --remap /turtle1/cmd_vel:=/cmd_vel
```

Before running that command in a terminal, checking the topic information with `ros2 topic list` shows information containing the following result:

```txt
/turtle1/cmd_vel
```

After running that command in a terminal, checking the node information with `ros2 topic list` shows information containing the following result:

```txt
/cmd_vel
```

::: tip What is this usually good for?
There's a package often used to control robots, `teleop_twist_keyboard`, which uses the topic name `/cmd_vel` when it runs. Take ROS2's most-used *Hello World stand-in package* — the little turtle package `turtlesim`: when you want to drive the little turtle in the window with a keyboard or other input device, the topic it uses for control is `/turtle1/cmd_vel`. If you want to control it with `teleop_twist_keyboard`, you have to change the two topics to one shared name before the data can flow and the little turtle can be driven. At that point you can use the approach above to change either side's topic name, for example changing `/turtle1/cmd_vel` to `/cmd_vel`.
:::

### 2. Changing the topic name with a launch file

launch files can be written in `Python`, `XML` or `YAML`, and all three can set the namespace and the name remapping.

::: important Before you use it...
When you use a `launch` file, remember to add the following at the `install` spot in `CMakeLists.txt`

```txt
install(DIRECTORY launch DESTINATION share/${PROJECT_NAME})
```

Of course, the `launch` files below cover the configuration for `C++` nodes; if you want the configuration for `Python` nodes, see the [launch file notes](./) further on
:::

#### ①. Writing the launch file in Python to set the namespace and name remapping (recommended)

When you write a launch file in `Python`, you can create the node object to be launched with the `Python` class `launch_ros.actions.Node`, and that object's constructor takes two arguments, `remappings` and `namespace`, to set the topic's **name** and **namespace**. An example:

```python
from launch import LaunchDesciption
from launch_ros.actions import Node

def generate_launch_description():

    return LaunchDesciption([
        # set the namespace
        Node(package="turtlesim", 
            executable="turtlesim_node", 
            namespace="t1"),
        # set the name remapping
        Node(package="turtlesim", 
            executable="turtlesim_node", 
            remappings=[("/turtle1/cmd_vel", "/cmd_vel")])
    ])
```

::: warning Note
The function name above **must** be `generate_launch_description`, otherwise ROS2 won't recognise and run the function.
:::

#### ②. Writing the launch file in XML to set the namespace and name remapping

When you write a launch file in `XML`, you can set the topic's **namespace** through the `namespace` argument that `node` provides, and change the topic name through the `remap` child tag inside the `node` tag. In the `remap` child tag, the `from` argument is the topic name being changed and the `to` argument is the topic name after the change. An example:

```xml
<launch>
    <!-- set the namespace -->
    <node pkg="turtlesim" exec="turtlesim_node" namespace="t1"/>
    <!-- set the name remapping -->
    <node pkg="turtlesim" exec="turtlesim_node">
        <remap from="/turtle1/cmd_vel" to="/cmd_vel" />
    </node>
</launch>
```

#### ③. Writing the launch file in YAML to set the namespace and name remapping

When you write a launch file in `YAML`, you can likewise set the topic's **namespace** through the `namespace` argument that `node` provides, and change the topic name through the `remap` property under the `node` properties. In `remap`, the `from` argument is the topic name being changed and the `to` argument is the topic name after the change. An example:

```yaml
launch:
# set the namespace
- node:
    pkg: "turtlesim"
    exec: "turtlesim_node"
    namespace: "t1"
# set the name remapping
- node:
    pkg: "turtlesim"
    exec: "turtlesim_node"
    remap: "ts1"
    - 
      from: "/turtle1/cmd_vel"
      to: "/cmd_vel"

```

### 3. Changing the topic name in code

When we write a topic, we are in fact doing the relevant setup inside the matching constructors that `rclcpp` and `rclpy` provide, and topics built from different types of topic name differ somewhat depending on where they hang. In other words, setting a topic name **in code** is pretty flexible too. So for topic-name changes in code, here we have to lay them out by **topic category**.

::: info Assumption
Assume that when creating the **C++** or **Python** packages and nodes, the namespace used is `ABC` and the node name is `XYZ`. The node creation here follows the previous chapter, [the part on rclcpp's API](./2025_03_14.md#_1-the-relevant-api-in-rclcpp) and [the part on rclpy's API](./2025_03_14.md#_2-the-relevant-api-in-rclpy)
:::

#### Topic types and how they relate to topic names

How a topic's name is set has some connection to the node's namespace and the node's name. Topic names can be roughly put into three types:

- **Global topics**

  **Property:** a global topic refers to the ROS system; it sits on the same level as the node's namespace, **hanging under the root directory**

  **Format:** a name defined starting with `/`; it has nothing to do with the `namespace` or the `node name`.

  Creating a publisher topic inside a custom node:

  **rclcpp example:**

  ```cpp
  public:
    MyNode():Node("XYZ", "ABC"){
        publisher_ = this->create_publisher<std_msgs::msgs::String>("/topic/chatter", 10);
    }
    ...
  private:
    rclcpp::Publisher<std_msgs::msgs::String>::SharedPtr publisher_;

  ```

  **rclpy example:**

  ```python
  class MyNode(Node):
    def __init__(self):
        super().__init__("XYZ", namespace="ABC")
        self.publisher_ = self.create_publisher(String, "/topic/chatter", 10);
  ```

  In this case the topic name used by that publisher is **"/topic/chatter"**; being a global topic, the name has nothing to do with the namespace `ABC` or the node name `XYZ`.

- **Relative topics**

  **Property:** the topic refers to the node's namespace, sitting on the same level as the node name, **hanging under the namespace**
  
  **Format:** a name defined not starting with `/`; it sets its topic name by reference to the `namespace`, and has nothing to do with the `node name`.

  Creating a publisher topic inside a custom node:

  **rclcpp example:**

  ```cpp
  public:
    MyNode():Node("XYZ", "ABC"){
        publisher_ = this->create_publisher<std_msgs::msgs::String>("topic/chatter", 10);
    }
    ...
  private:
    rclcpp::Publisher<std_msgs::msgs::String>::SharedPtr publisher_;

  ```

  **rclpy example:**

  ```python
  class MyNode(Node):
    def __init__(self):
        super().__init__("XYZ", namespace="ABC")
        self.publisher_ = self.create_publisher(String, "topic/chatter", 10);
  ```

  ::: caution
  Both of these use **"topic/chatter"** rather than the **"/topic/chatter"** used earlier — mind the difference!
  :::

  In this case the topic name used by that publisher is **"/ABC/topic/chatter"**; being a relative topic, the name is tied to the namespace `ABC` and has nothing to do with the node name `XYZ`.

- **Private topics**

  **Property:** the topic refers to the node name, is a child of the node name, **hanging under the node name**

  **Format:** a name defined not starting with `/`; it sets its topic name by reference to both the `namespace` and the `node name`.

  Creating a publisher topic inside a custom node:

  **rclcpp example:**

  ```cpp
  public:
    MyNode():Node("XYZ", "ABC"){
        publisher_ = this->create_publisher<std_msgs::msgs::String>("~/topic/chatter", 10);
    }
    ...
  private:
    rclcpp::Publisher<std_msgs::msgs::String>::SharedPtr publisher_;

  ```

  **rclpy example:**

  ```python
  class MyNode(Node):
    def __init__(self):
        super().__init__("XYZ", namespace="ABC")
        self.publisher_ = self.create_publisher(String, "~/topic/chatter", 10);
  ```

  ::: caution
  Both of these use **"~/topic/chatter"** rather than the **"/topic/chatter"** used earlier — mind the difference!
  :::

  In this case the topic name used by that publisher is **"/ABC/XYZ/topic/chatter"**; being a private topic, the name is tied to both the namespace `ABC` and the node name `XYZ`.

---

In short, apart from the path descriptions, the rules for setting topic names are basically the same in rclcpp and rclpy, and the rules above apply just as well to the `ros2 run` command and to `launch` files.
